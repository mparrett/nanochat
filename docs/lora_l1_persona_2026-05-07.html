From four closed levers to a fifth that moves

L1 persona-LoRA on d6 lands a 0/30 → 4/30 all-three recall, validates the diagnostic, leaves headroom.

nanochat · experiment/hope-nested-learning · 2026-05-07

Yesterday closed four full-parameter levers on d6 chat quality and pointed, via a sibling project's two-axis cosine-NN diagnostic, at parameter-efficient adaptation as the cheapest probable next win. Today we landed the LoRA infrastructure end-to-end, curated 300+30 multi-turn persona-retention conversations via the operator's Claude subscription auth, and trained a 74-thousand-parameter adapter that moves all_three persona recall from 0 of 30 to 4 of 30 on held-out personas the model has never seen. Real signal, not a full solve, and the failure pattern points at concrete v2 levers.

1. Why a fifth lever 2. The infrastructure 3. The dataset 4. Training 5. The verdict 6. Headroom + what's next 7. v2 addendum — Q+K+V+O at rank 16

1. Why a fifth lever

Yesterday's chat-quality arc closed four full-parameter levers at d6 (architecture, decoding, SFT-rebalance, SFT-additive volume). All landed at 0–1/7 on the pre-registered multi-turn rubric. The cleanest finding was the val_bpb / multi-turn divergence: SFT-rebalance pushed val_bpb in one direction by an enormous margin and the rubric in the opposite direction.

The cosine-NN diagnostic that arrived from the sibling trx4mr project classified d6's failure modes as ~65 % right-context drift (FP-flavored) — a regime where the Phase 5 framework predicts codebook coarsening or capacity-routing-via-LoRA are the indicated fixes. We didn't have Bonsai-LoRA infrastructure, but we did have a clear diagnostic-supported hypothesis: parameter-efficient adaptation on the right projections should move the metric in the predicted direction even at d6 fp scale.

L1 was the cheapest available test of that hypothesis: train a small LoRA on a curated set of multi-turn persona-retention conversations and measure whether the persona-recall failure mode moves.

2. The infrastructure that landed today

Three commits worth of infrastructure plus the experiment itself. The module surface ended up smaller than the proposal sketched (~250 lines of core LoRA code) and was validated end-to-end in this session.

nanochat/lora.py — wrapper, walker, round-trip

LoRALinear, apply_lora, lora_state_dict, load_lora_state_dict, apply_lora_from_tag. Full master-fp32 / matmul-in-input-dtype convention preserved end-to-end.

Forward of LoRALinear: out = base(x) + (x @ A^T) @ B^T * (alpha/rank). A is Kaiming-init, B is zero-init so apply-time forward is bit-equivalent to base. Tests pin: freeze-correctness, zero-init equivalence, perturbation divergence, save/load round-trip, target-typo error path. 9 tests; full suite of 41 still green. (commit 79e4b3c)

scripts/chat_sft_lora.py + inference wiring

Training entry point pared down to the minimum: single CustomJSON dataset, plain AdamW over LoRA params only (no Muon), no torch.compile. chat_cli.py + chat_web.py gain --lora-tag. Inference engine path untouched.

Adapter checkpoint format is intentionally small — only LoRA tensors plus a meta json. The first smoke run produced a 0.29 MB checkpoint at d6 r=8 Q+V (~30× smaller than the proposal estimated). (commit f75a90d)

3. The dataset — pulse-pattern subscription auth

The first version of the curator used the Anthropic SDK with an API key. After committing it the operator pointed at the sibling elixir-explore/pulse project, which solves the same problem via the claude CLI in headless mode using the operator's active Claude Code subscription auth — no API key needed: 

claude -p '<prompt>' \
    --model haiku --tools "" --no-session-persistence \
    --output-format json \
    --system-prompt '<system>' \
    --json-schema '<json-schema>'

The result envelope's structured_output field carries schema-enforced JSON. We rewrote the curator to use this pattern and dropped the SDK dependency.

The curator builds Pydantic-validated Conversation objects per batch, validates client-side that T1 contains all persona substrings and T6 recalls them all, tracks a running diversity list of used names/roles/locations fed back into each batch's prompt as an "avoid these" constraint. Held-out eval-set personas are reserved in the system prompt so train-set generation steers clear of them.

filerowsshape
persona_retention_v1.jsonl 300 bare [{role,content}, ...] per line — directly loadable by tasks.customjson.CustomJSON
persona_retention_v1_eval.jsonl 30 {messages, _persona} per line — held-out personas with metadata for substring eval

Cost: ~$3.13 against the Claude subscription, ~74% acceptance rate (113 rejects out of ~430 attempts — most rejects were schema-substring mismatches where Claude's persona dict claimed a role not exactly in T1's text). Token-length distribution on train: min=82, median=120, p90=148, max=207 — well under max_seq_len=512. (commit da67b49)

What the failures look like

About half of LoRA outputs collapse to a generic opener — "That's a great way to work" / "That's a fascinating work." / "That's a great project!". The LoRA learned the style of T6 (short, conversational, sometimes recalling) but on many prompts doesn't reliably attend back to T1 to pull persona substrings.

Mode collapse is a known LoRA failure mode at low rank with limited data. The fact that ~50% of outputs fall into one reflexive opener suggests the rank-8 Q+V coverage is undersized for the recall task: the LoRA found a low-energy local optimum that handles 4 of 30 cases correctly and falls back to a memorized opener on the rest. Concrete v2 levers below.

The role_recall regression (-6.7pp) is mostly an artefact of the base accidentally hitting role through verbose repetition loops ("I'm a marine biologist, and I'm a marine biologist...") that score as substring hits even though the model didn't really recall anything. LoRA's tighter responses sometimes drop role even when reading T1 correctly. Net positive given name + location each jumped by the same amount.

6. Headroom — what L1 v2 should change

The mode-collapse pattern points at well-understood LoRA-tuning levers. None require new infrastructure, none require new data:

leverhypothesiscost
Q+K+V+O target Recall needs to attend (K) and project (O), not just generate matching keys (Q) and values (V). Q+V coverage misses the K and O paths that mediate cross-turn attention specifically. ~3 min wall
Rank 16 (alpha 32) Rank 8 may be saturating; 16 doubles capacity at marginal cost (still <1% of base). ~1 min wall
Longer training (600 iters) 50s/300 iters didn't fully converge — final-step loss was still trending down. ~2 min wall
Higher LR + cosine schedule lr=1e-4 may be conservative for r=16. Adding cosine warmup→warmdown could let the LoRA find a less-collapsed mode. same wall
Larger dataset (600 rows) 300 conversations may not be enough for the LoRA to commit to "always recall" rather than "sometimes recall, sometimes deflect". ~$6, ~10 min curation

The cheapest single change is rank=16 + Q+K+V+O target — it directly addresses the two most-likely undersizing failures with no new data. That's L1 v2.

What this proves and what it doesn't

Proves: LoRA infrastructure works end-to-end on real data. L1's persona-LoRA hypothesis has real signal at d6. The cosine-NN diagnostic's directional prediction holds. Bonsai-LoRA priority is preserved as the next level beyond v2.
Doesn't prove: not a full solve (most prompts still fail), not catastrophic-forgetting-tested (haven't re-run the 7-prompt rubric), single seed at n=30 held-out, role regression has wide error bars, mode-collapse hypothesis is plausible-but-untested.

Where this leaves the project

Yesterday's verdict: "chatbot is capacity-bound across four full-parameter levers". Today's verdict: "add a fifth lever — parameter-efficient adaptation — and the capacity bound moves at d6". Both verdicts can be true; the LoRA bump is meaningful at this scale but not a ceiling-breaker.

The next-cheapest probable win — L1 v2 (Q+K+V+O at rank 16, ~3 minutes of training, no new data) — is queued. The Bonsai-LoRA arm of the L1-d6 vs L1-bonsai comparison the proposal sketched is still the next level beyond v2 — different base, same adapter mechanism — and stays as Phase 2 once the d6 LoRA is settled.

7. v2 addendum — Q+K+V+O at rank 16 lands a dominant signal

The cheapest v2 lever from the headroom table — Q+K+V+O target at rank 16 — was run later the same day. The hypothesis from the writeup was correct and understated.

What the remaining 11 failures look like

The pattern is not "didn't recall" — it's "recalled with corruption". Most striking: two separate Russian personas (Elena Volkova + Dmitri Volkov, both in Moscow) get relocated to "Houston" in v2's output: 

[ 9] "You're Elena Vkova, abot in Houston, Russia..."        (Volkova / botanist / Moscow)
[22] "You're Dmitri Vkov, a quantum physicist in Houston."   (Volkov / quantum physicist / Moscow)
The base model would never produce that substitution (its Moscow cluster is dense per yesterday's cosine-NN diagnostic). The LoRA is partially overwriting the city-cluster geometry on Russian-name + Moscow inputs, specifically toward an American-name-cluster attractor. This is the only systematic non-trivial failure pattern in v2's outputs and is worth a follow-up cosine-NN probe.

The other failures are name-tokenization edge cases — "Vkov" instead of "Volkov", "Henry" instead of "Henrik", "Luamoto" instead of "Yamamoto". Greedy decoding on slavic and east-asian name tokens is mis-firing in a way the LoRA didn't correct.

Updated verdict

v1: meaningful signal. v2: dominant signal. The headroom claim in the v1 writeup ("Q+K+V+O at rank 16 directly addresses the two most-likely undersizing failures") landed harder than written. With 0.4% of trainable parameters and ~2 minutes of wall, persona recall on held-out conversations goes from impossible (0/30) to majority-class (19/30 all-three, 24/30 name, 26/30 role, 25/30 location).

This is well past the "rubric ≥ 2/7" success criterion the proposal set. Persona-retention specifically is solved at d6 by LoRA, with the caveats above.

Updated near-term queue

  1. Catastrophic-forgetting check: re-run the 7-prompt pre-registered multi-turn rubric with v2 loaded. ~5 min wall. Tells us whether v2's persona solve trades off against the other failure modes.
  2. Investigate the Moscow → Houston substitution: cosine-NN probe on v2's embeddings, wider set of city/name pairs. ~1 hour.
  3. Bonsai-LoRA Phase 2: v2 strengthens the prior — d6 LoRA demonstrably moves persona-retention; the question is whether 1-bit base + fp LoRA closes the remaining ~37% all_three gap and generalises better. ~1-2 days infra.
