I’d try one no-rewrite lever before MLX/MSL: stop optimizing `s/iter`; optimize `tokens/sec` by amortizing Muon.

Given your profile numbers, one microbatch costs ~449 ms fwd+bwd and each optimizer step costs ~1,696 ms. Keeping `device_batch_size=32` but increasing `--total-batch-size` uses gradient accumulation without more MPS memory:

| accum | total batch | est. tok/s | same-token wall speedup |
|---:|---:|---:|---:|
| 1 | 16,384 | 7.6k | 1.0x |
| 4 | 65,536 | 18.8k | 2.5x |
| 8 | 131,072 | 24.8k | 3.3x |
| 16 | 262,144 | 29.5k | 3.9x |

That trades fewer optimizer updates for the same token budget, so it needs validation, but it is the cleanest plausible 1.5-2x+ path already supported by `scripts/base_train.py`.

Other concrete takes:

1. **Muon fp16 orthogonalization on M2 is worth testing.** I ran a synthetic MPS bench on the current repo/Torch 2.11. For d12-shaped Polar Express groups, fp16 was ~15-21% faster than fp32 and finite; bf16 was much slower. I would add an env flag for only `X = g.to(torch.float16)` inside [nanochat/optim.py](/Users/matt/projects-new/3p/nanochat/nanochat/optim.py:137), then cast back to param dtype as you already do. Full pretrain validation required.

2. **`ve_gate` should probably not be in Muon.** [setup_optimizer](/Users/matt/projects-new/3p/nanochat/nanochat/gpt.py:379) puts all transformer 2D params in Muon, including `(6,12)` / `(12,12)` gate matrices. That burns a whole Polar Express group for hundreds of parameters. Move those to AdamW. It is probably a small win, but almost no risk.

3. **MLP up/down canonicalization is possible but second priority.** Transpose wide MLP `c_proj` grads into the tall `(4d,d)` group, with per-param LR multipliers, so MLP up/down share one Muon call. My synthetic bench did not show a big win, but the implementation is much cheaper than MLX/MSL.

4. **`ns_steps=3` is a real candidate, but not because it “converges to numerical precision.”** On random d6/d12-shaped tensors, ns3 vs ns5 differed materially: relative diff around `0.6`, cosine roughly `0.80-0.94`. So the identical early loss means “training tolerates the different update,” not “same update.” Validate iso-token d6, then d12, with final val bpb and update cosine logs.

5. **`torch.mps.compile_shader` is not the cheap path for this bottleneck.** It lets you call custom MSL kernels from Python, but fusing Polar Express means writing tiled batched GEMMs plus reductions/state updates, not just fusing elementwise glue. A cheap shader can help elementwise tails; it will not erase the matmul loop wall. PyTorch docs: [compile_shader](https://docs.pytorch.org/docs/stable/generated/torch.mps.compile_shader.html).

6. **MLX two-week estimate is plausible for a research-only port, optimistic for nanochat parity.** MLX has compile support for full training graphs and optimizer state, and its unified-memory/lazy model fits this workload well ([MLX overview](https://ml-explore.github.io/mlx/build/html/index.html), [compile docs](https://ml-explore.github.io/mlx/build/html/usage/compile.html)). I’d budget 1-2 days first for an optimizer-only MLX Muon benchmark on fake d12 tensors. If that doesn’t beat PyTorch meaningfully, don’t port yet.

7. **For Hope/Nested Learning, avoid token loops from day one.** The OpenReview abstract frames Hope around self-modifying sequence modules and continuum memory ([OpenReview](https://openreview.net/forum?id=nbMeRvNb7A)). A literal per-token Python loop over `M_t = alpha M_{t-1} + v k^T` will be catastrophic on MPS. Start with detached/chunked linear-attention style memory, fixed shapes, static compile, and a synthetic recall task before touching full pretrain.
