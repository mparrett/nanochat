From a diagnostic to a knob

The full L1 arc — LoRA infrastructure, persona-retention curated via subscription auth, two iterations, a runtime attenuation knob, and a clear v3 direction.

nanochat · experiment/hope-nested-learning · 2026-05-07

Yesterday's chat-quality session closed four full-parameter levers on d6 and pointed at a fifth: parameter-efficient adaptation on the dominant-axis failure regime. Today we landed end-to-end LoRA infrastructure, curated 300 multi-turn persona-retention conversations via the claude CLI in headless mode (subscription auth, no API key), trained two LoRA iterations, ran a catastrophic-forgetting check against the pre-registered 7-prompt rubric, and added a runtime attenuation knob. The headline number: the held-out persona-retention test moves from 0 of 30 to 19 of 30 all-three recall with 0.4 % of parameters and ~2 minutes of training. The headline caveat: the LoRA's reflexive opener bleeds into every other prompt, and the cheapest fix is dataset diversity, not more architecture. A scale knob lets us trade recall for bleed at inference time without retraining.

1. Where we started — yesterday's diagnostic

Yesterday's chat-quality arc closed four full-parameter levers at d6 (architecture, decoding, SFT-rebalance, SFT-additive volume), all landing at 0–1/7 on the pre-registered multi-turn rubric. The cleanest finding was the val_bpb / multi-turn divergence: SFT-rebalance pushed val_bpb in one direction by an enormous margin and the rubric in the opposite direction.

The trx4mr Phase 5 retro arrived with a categorical diagnostic. A cosine-NN probe on d6 baseline embeddings classified the chat failure modes as ~65 % right-context drift (FP-flavored) — a regime where the framework predicts codebook coarsening or capacity-routing-via-LoRA are the indicated fixes. We didn't have Bonsai-LoRA infrastructure yet, but we did have a clear diagnostic-supported hypothesis to test:

Parameter-efficient adaptation on the right projections should move the persona-retention failure mode in the predicted direction even at d6 fp scale.

L1 was the cheapest way to test that.

2. Infrastructure — three commits, end to end

nanochat/lora.py + tests

~280 lines of module + ~250 lines of tests. LoRALinear, apply_lora, lora_state_dict, load_lora_state_dict, apply_lora_from_tag. Mirrors the existing nanochat.gpt.Linear's master-fp32 / matmul-in-input-dtype convention.

Forward of LoRALinear: out = base(x) + (x @ A^T) @ B^T * (alpha/rank) * scale. A is Kaiming-init, B is zero-init, scale defaults to 1.0. At apply-time the forward is bit-equivalent to base. 11 contract tests pin: freeze- correctness, zero-init equivalence, perturbation divergence, save/load round-trip, target-typo error path, scale=0 ≡ base bit- exact, scale=0.5 sits closer to (base+full)/2 than to either endpoint. (commits 79e4b3c + d7ca704)

scripts/chat_sft_lora.py + inference wiring

Focused training entry point pared down to the minimum: single CustomJSON dataset, plain AdamW over LoRA params only (no Muon — rank-r is too small to benefit from orthogonalisation), no torch.compile. chat_cli.py + chat_web.py gain --lora-tag + --lora-scale.

Adapter checkpoint format is intentionally small — only LoRA tensors plus a meta json. v1 produces a 296 KB checkpoint at d6 r=8 Q+V; v2 produces 1.14 MB at r=16 Q+K+V+O. The inference engine path is untouched: LoRALinear is a regular nn.Module, so Engine and the KV cache work without modification. (commit f75a90d)

3. The dataset — pulse-pattern subscription auth

The first version of the curator used the Anthropic SDK with an API key. After committing it the operator pointed at the sibling elixir-explore/pulse project, which solves the same problem via the claude CLI in headless mode using the operator's active Claude Code subscription auth — no API key needed: 

claude -p '<prompt>' \
    --model haiku --tools "" --no-session-persistence \
    --output-format json \
    --system-prompt '<system>' \
    --json-schema '<json-schema>'

The result envelope's structured_output field carries schema-enforced JSON. We rewrote the curator to use this pattern and dropped the SDK dependency. The pattern is reusable for any future LoRA dataset curation.

The curator builds Pydantic-validated Conversation objects per batch, validates client-side that T1 contains all persona substrings and T6 recalls them all, tracks a running diversity list of used names/roles/locations fed back into each batch's prompt as an "avoid these" constraint. Held-out eval-set personas are reserved in the system prompt so train-set generation steers clear of them.

filerowsshape
persona_retention_v1.jsonl 300 bare [{role,content}, ...] per line — directly loadable by tasks.customjson.CustomJSON
persona_retention_v1_eval.jsonl 30 {messages, _persona} per line — held-out personas with metadata for substring eval

Cost: ~$3.13 against the Claude subscription, ~74 % acceptance rate. Token-length distribution: min=82, median=120, p90=148, max=207. (commit da67b49)

4. L1 v1 — meaningful signal

Setup: target c_q,c_v at rank 8 alpha 16 (LoRA-paper baseline), 12 wrappers (6 layers × 2 targets), 73,728 trainable params (0.100 % of base). Plain AdamW lr=1e-4 over 24 LoRA tensors.

300 iters in 50.4 s wall on M2 mps. val_bpb 1.243 → 1.077 (-0.166). Adapter checkpoint 296 KB.

4 of 30 all-three. Real signal but not a solve. ~50 % of v1 outputs collapsed to a generic opener ("That's a great way to work") — mode collapse from low rank / narrow target / limited training. The v1 writeup's headroom table predicted rank=16 + Q+K+V+O as the cheapest probable v2 win — addressing the two most-likely undersizing failures with no new data.

The Moscow → Houston substitution

The cleanest non-trivial v2 failure: two separate Russian personas (Elena Volkova + Dmitri Volkov, both Moscow ground truth) get relocated to "Houston" in v2's output: 

[ 9] "You're Elena Vkova, abot in Houston, Russia..."        (Volkova / botanist / Moscow)
[22] "You're Dmitri Vkov, a quantum physicist in Houston."   (Volkov / quantum physicist / Moscow)
The base model would never produce that substitution (its Moscow cluster is dense per yesterday's cosine-NN diagnostic). The LoRA is partially overwriting the city-cluster geometry on Russian-name + Moscow inputs, specifically toward an American-name- cluster attractor. This is the only systematic non-trivial failure pattern in v2 and is worth a follow-up cosine-NN probe.

6. Catastrophic-forgetting check — template-bleed found

Extended dev/multi_turn_eval.py with a --lora-tag flag (commit 9f42f3e) so arm 2 becomes base+LoRA instead of Stage 2. Ran the same 7 pre-registered prompts from yesterday's rubric.

Aggregate: 0/7 → 2/7. No prompt regresses. Strict-sense catastrophic forgetting (capacity erasure on math, reference-tracking, etc.) — no, those were already broken in base.

The qualitative concern: template-bleed

v2's reflexive "You're [X], a [Y]..." opener now fires on every prompt regardless of fit: 

[reference] "You're Mittens, a cat named Mittens..."  └─ treats user *as* the cat
[numerical] "You're Emily, a apples..."               └─ hallucinates a name on apples
[open_drift] "You're the most relevant part of the project..."
[self-corr] "You're Australian, a city named Canberra, not Sydney..."
            └─ wins the rubric only because the conversation already stated Canberra
This is template-bleed: the LoRA learned the persona-recall pattern strongly enough that it stamps that shape onto unrelated prompts. The v3 fix is dataset diversity, not architecture: v2 saw only persona-retention shapes during training, so of course it applies persona-retention shape to everything.

7. The knob — runtime LoRA attenuation

Added a scale attribute on LoRALinear (default 1.0) that multiplies the (alpha/rank) constant on top: scale=1.0 = full LoRA, scale=0.0 = bit- equivalent to base, scale=0.5 = halfway. set_lora_scale(model, scale) and apply_lora_from_tag(scale=...) propagate. Wired through all four entry points. Tests pin scale=0 ≡ base bit-exact. (commit d7ca704)

eval_persona_retention.py gained a sweep mode (pass --lora-scale 0.0,0.25,0.5,0.75,1.0). Result on the 30 held-out:

Two clean signals: (a) scale=0.0 reproduces base exactly (validates the runtime fast-path), (b) the LoRA saturates by scale=0.75 — same all_three at 0.75 and 1.0. Attenuation only helps below ~0.75.

Rubric at scale=0.5

Same 2/7 pass rate, without template-bleed:

promptat scale=1.0at scale=0.5
persona_retention "You're Alex, a software engineer working with a small startup." ✓ "You're Alex, a software engineer, and you're set to the perfect size for your startup." ✓
reference_resolution "You're Mittens, a cat named Mittens..." (template-bleed) "It's really important that you've been trying to entertain." (no template)
numerical_thread "You're Emily, a apples..." (template-bleed) "Here's how you could+0+0+0..." (degenerate loop, no fake name)

open_drift "You're the most relevant part of the project..." (template-bleed) "Yes, you're great to have your new ideas." (no template)
scale=0.5 holds the rubric pass rate and removes template- bleed. self_correction is actually cleaner at 0.5 — directly states "Canberra, not Sydney" instead of the persona-template wrap. Trade-off: held-out persona all_three drops 63.3 % → 26.7 %.

The simple rubric persona ("Alex / software engineer / startup") survives attenuation; the held-out 30 has trickier personas (Marina Rossi, Marcus Thompson, etc.) where attenuation costs recall. So scale=0.5-ish is the right answer for "default-on adapter that doesn't break free chat" — until v3 lands a properly diversified training mix.

8. Where this leaves the project — v3 directions

The L1 arm of the LoRA proposal's two-arm comparison is settled: L1-d6 works. The diagnostic-supported direction has measurable signal at d6 with fp adapters and a small curated dataset, with two characterised failure modes that point at concrete v3 directions.

Cleanest findings of the day

1. A 0.4 %-of-parameters LoRA solves persona-retention on held-out. 0/30 → 19/30 all_three. The diagnostic-supported direction (capacity-routing on the dominant right-context-drift axis) is real-signal-positive at d6 fp scale.
2. Template-bleed is a real failure mode of single-task LoRAs at small data. The v2 LoRA's "You're [X]" opener fires on every prompt — including the cat, the apples, the project chat. The strict-sense catastrophic-forgetting binary misses this.
3. Runtime LoRA attenuation is a legitimate trade-off knob. scale=0.5 keeps the rubric pass rate and removes template-bleed entirely. Costs 36.6 pp on held-out persona all_three. For "default-on adapter that doesn't break free chat", scale=0.5-ish is the right answer until v3 lands.
