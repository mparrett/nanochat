## Run config

```
scripts/chat_sft.py --model-tag=d8_overnight --model-step=5000 \
  --sft-tag=d8_overnight \
  --num-iterations=375 \
  --device-batch-size=8 --total-batch-size=16384 \
  --eval-every=50 --eval-tokens=524288 \
  --chatcore-every=-1 \
  --save-every=100 --save-keep-last-n=2 \
  --grad-checkpoint \
  --run=d8_sft_overnight
```

- **Total tokens trained:** 16,384 × 375 ≈ **6.1 M tokens**.
- **vs d6 canonical SFT:** 65,536 × 375 ≈ 24.6 M tokens (**4× more**).
- Single grad-accum chosen deliberately: kickoff doc said "if capacity
  allows the bigger batch, prefer it; otherwise single-grad-accum is
  fine for a first pass." Capacity allowed batch=8 with `--grad-checkpoint
  + compile` (the new wiring in `chat_sft.py` from commit `7e5f974`).
- `--eval-tokens=524288` overrides the default 21M (which would have
  stalled the run with ~30 min evals per checkpoint).

Two phases visible:

Net improvement: −0.095 bpb (10.9 % relative) from step 0 to step 374.
But the absolute floor (0.7724) is well above d6 references (0.66-0.67).

### What drives the gap to d6_stage2's 0.1744

1. **SpellingBee 69% vs 95% (−0.262 centered)** — biggest delta.
   d6_stage2 SFT memorized the spell-out-and-count template hard;
   d8 here only partially memorized it. 4× fewer SFT training tokens
   is the most direct explanation (insufficient passes over SpellingBee
   training distribution to lock the template).
2. **Categorical tasks below random baseline (sum −0.080 centered).**
   The d8 SFT didn't lock the MCQ-letter output format. Output
   distribution shifted enough during SFT to perturb letter-token
   probabilities, but not enough to learn the task. d6_stage2 hugged
   baseline (sum +0.086 centered) — same compute regime, but more
   stable token-format calibration.
3. **GSM8K + HumanEval = 0** — same as d6_stage2. Not the
   differentiator. d8/d6 at this scale lack the parameter budget for
   multi-step reasoning or program synthesis regardless of recipe.

So the entire 0.0994 gap from d6_stage2 to d8 lives in two places:
SpellingBee (−0.044 contribution to mean) and MCQ tasks (−0.027
contribution). Both are SFT-recipe-driven, not architecture-driven.

## What this run answered (and didn't)

**Answered:**
- d8 SFT trains stably on M2 24 GB with `--grad-checkpoint + compile +
  device-batch=8`. No OOM, no fragmentation, no NaN, smooth descent
  through 375 opt steps.
- The `--grad-checkpoint` wiring in `chat_sft.py` (commit `7e5f974`)
  works end-to-end and was validated on a 2-iter smoke before the
  real run.
- Wall time on a quiet M2 was **48.5 min**, far below the 3-4 h
  estimate. The 26 % sys-CPU paging share from the pretrain didn't
  recur — 10.5 % sys this time.
- ChatCORE infrastructure (`scripts/chat_eval.py`) ran cleanly on the
  d8 ckpt; `mps_release_cache()` fix held through all categorical
  batches and 300 generative samples. No OOM.

**Not answered:**
- **Does d8 SFT match d6_stage2 ChatCORE if given matched effective
  tokens?** Today's run was 4× under-tokened. The natural follow-up
  is an SFT-A2 pass at `--total-batch-size=65536 --device-batch-size=8`
  (grad-accum=8), ~3.2 h projected on M2 with `--grad-checkpoint`.
- **Is the SpellingBee shortfall purely token-budget or also model
  capacity?** d8 has ~2.4× the per-token compute of d6 — it should
  *easier* to memorize the SpellingBee template at matched tokens, not
  harder. A2-style retry should disambiguate.
- **Canonical ChatCORE (`-x` unset, full test sets, ~1.5 h wall).**
  Today's `-x 100` has per-task stderr around ±5 % (categorical) to
  ±10 % (generative). The 69 % SpellingBee number especially could be
  ±5 absolute points. Not worth re-running unless we're publishing.

## Implications for next steps

In rough priority order:

1. **SFT-A2: d8 retry at total-batch=65536, grad-accum=8.**
   Most direct test of the "under-tokened" hypothesis. Same base ckpt
   (`d8_overnight`), same 375 opt steps, but 4× more effective tokens
   per step. Save under a new `--sft-tag=d8_overnight_a2`. ~3 h wall.
   If ChatCORE clears the 0.15 threshold and SpellingBee hits ≥90 %,
   the recipe-budget diagnosis is confirmed. If it doesn't, the
   bottleneck is base-model quality (sub-Chinchilla d8).

2. **Or: extend d8 base pretrain to higher token budget first.**
   Today's d8 base trained 82 M tokens (~5 % of Chinchilla). A d8 base
   retrained to ~500 M-1 B tokens (Chinchilla-ish) might lift the SFT
   floor enough that even single-accum SFT clears the threshold. Long
   wall (~5-10 h pretrain). Costlier than option 1 but a better answer
   to "what's d8's actual ChatCORE potential?"

3. **Canonical CORE (`--max-per-task=500`) on the d8 base** — already
   queued from `docs/d8_baseline_2026-05-10.md`, not blocked on SFT.
   Independent diagnostic of "is the base model the bottleneck."

4. **`learned_scale` (P1)** — still paused per yesterday's handoff,
   not architecture-blocked by today's result. Pick up when the d8
   thread settles.
