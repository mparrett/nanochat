Andrej Karpathy's nanochat ships a tuned recipe for getting through tokenizer training, pretraining, and supervised fine-tuning on a MacBook M3 Max. We have an M2 with 24GB. The README warns: "You will not get far on your Macbook." We got pretty far. Here's what it took, what broke, and the two real bugs we hit along the way — including one we're filing upstream.

"The capital of France is Paris. It is a city known for its historical landmarks and cultural institutions such as the Eiffel Tower and the Louvre Museum…" — our model, after 5h of total training
01 / The plan

What we set out to do

nanochat is a single-GPU-node training harness — tokenizer, base pretraining, SFT, RL, eval, inference, web UI — designed to be a clean reference codebase rather than a configurable framework. Karpathy's runs/runcpu.sh bundles the whole thing into one bash script, tuned for an M3 Max in roughly 45 minutes.

Our M2 has fewer GPU cores and roughly a quarter of the memory bandwidth. We expected 3–5× slower wall-clock and went in willing to take an overnight run to find out where the M3-tuned recipe would or wouldn't translate. Spoiler: the speed delta was the easy part — the interesting failures were data-pipeline edge cases that the M3 Max happens to step around.

02 / The pipeline

Architecture in one diagram

ClimbMix-400B
9 shards (~800MB) → BPE tokenizer
32k vocab → Pretrain
d6, 73M params, 5000 iters → SFT
SmolTalk + identity, 1500 iters → chat_cli / chat_web Bracketed by a single complexity dial — depth=6. Width, heads, learning rate, weight decay, training horizon all derive from depth so any size produces a compute-optimal model.

The model is a vanilla-ish GPT with rotary embeddings, untied embed/lm_head, ReLU² MLPs, RMSNorm without learnable params, GQA attention, and Flash Attention 3 on Hopper+ with an SDPA fallback for everything else (including MPS). All artifacts go under $NANOCHAT_BASE_DIR — datasets, tokenizer pickle, checkpoints, the lot.

What's notable about the codebase: nearly every "hyperparameter" is a derived quantity, not a setting. There are no model factories, no config objects, no plugin systems. Want a different model size? Change --depth. The codebase is small enough to read end-to-end in an afternoon, which made the bug hunts that follow possible.

03 / The journey

What broke and how we fixed it

INCIDENT 01
Bug Upstream issue #590 Patched via PR #610

SFT loss goes NaN at step 4, deterministically

First training step looks fine, second is fine, third is fine, fourth is NaN and never recovers. Tested everything: lower learning rate (10× smaller across the three optimizer groups), no inherited optimizer state, aggressive linear warmup. None of it mattered. The NaN trigger isn't a hyperparameter.

Found it by reading the open issues. F.cross_entropy(reduction='mean') divides by the number of non-ignored target tokens. When all targets are -1 (the ignore index), it divides by zero. CUDA tends to mask this with autograd glue at certain optimizer state; MPS does not. The cure is to trap the case before cross_entropy sees it: 

if loss_reduction == 'mean' and not (targets != -1).any():
    # All targets ignored — return graph-connected zero so
    # grad-accum sees no contribution rather than poisoning.
    return logits.sum() * 0.0
INCIDENT 02
Bug Found locally Patched in chat_sft.py

The dataloader silently lobotomized the model

With Incident 01 patched, SFT ran cleanly to the end. Loss displayed a beautiful exponential decay from 1.89 to 1e-5. The smoke test came back: "juven neurotransmit�esterol meticul…" Pure token soup. The val_bpb had gone from 1.07 (start) to 5.07 (end) — the model got worse.

We instrumented the training loop with (y != -1).sum() per step. The numbers told the story:

stepn_valid / total% valid
12,911 / 16,38417.8%
23,487 / 16,38421.3%
34,406 / 16,38426.9%
4 — 490 / 16,3840.0%

Forty-six of forty-nine steps had zero valid training targets. The model was getting no gradient updates for 94% of the run. The exponential decay we were watching was the EMA loss display draining toward zero because Incident 01's fix was returning 0.0 for fully-masked batches. Honest gradient, dishonest readout.

Root cause was in sft_data_generator_bos_bestfit. It maintains a buffer of 100 conversations and only pops them when one fits in max_seq_len + 1 = 513 tokens. SmolTalk has many conversations longer than 513 tokens. Once the small ones drain in steps 1–3, the buffer fills permanently with over-length entries that can never fit any row, every row gets BOS-padded with mask=0, and consumed never advances. The it counter keeps incrementing — the appearance of training. The fix is straightforward: detect the lockup state and discard the over-length convs. 

elif len(row) == 0:
    # Fresh row, nothing fits → buffer must be locked with
    # conversations larger than row_capacity. Drop them so
    # refill_buffer() can pull fresh data.
    n_dropped = len(conv_buffer)
    consumed += n_dropped * ddp_world_size
    conv_buffer.clear()
    continue

After patching: median 29% valid tokens per step, zero fully-masked steps, loss descended honestly from 1.89 to 1.40. Worth filing upstream — current code silently fails on any setup where max_seq_len falls below the dataset's median conversation length.

INCIDENT 03
Operational Process hygiene

Defaults that nuke wall-clock; orphaned workers that hang the next run

chat_sft defaults --chatcore-every to 200, meaning the full ChatCORE benchmark suite (ARC, MMLU, GSM8K, HumanEval, SpellingBee) runs every 200 steps. On M2 each pass takes hours. --eval-every=-1 skips intermediate val evals but not the one at last_step — the default --eval-tokens=21M means a ~30-minute eval before the save block runs. Pass --eval-tokens=0 to actually skip it.

Less obvious: a multiprocessing worker from an earlier debug probe stayed running for nearly three hours at 22% CPU after I'd "killed" the parent. It pinned the Metal context. The next training launch hung at 0% CPU after step 1 with no error. pgrep -lf python between runs is now muscle memory.

05 / What the model can actually do

Inference notes

The model nails Paris, namechecks the Eiffel Tower and the Louvre, and follows the chat template ("Hello! How can I help you today?"). Past a sentence or two it loses the thread: in our test runs it confidently described "a soft-l ride could also be associated with those around the world" as part of an explanation of why the sky is blue.

On sampling: standard advice (temperature 0.8, top-k 50) works fine here, but tightening either too much (we tried temp=0.5, k=20) collapses the model into degenerate loops — at one point it emitted "a blue-batch called 'cending' and 'cending'" roughly thirty times in a single response. Tiny models have narrow, deep attractors in token space; they need some sampling jitter to escape them, even at the cost of coherence. RLHF would flatten these out, but that's the next phase.

06 / Takeaways

What I'd do differently

  1. Instrument before you wait. When loss decays to suspiciously low values, add a per-step counter for the actual training signal immediately. Don't run for an hour assuming overfitting if there's a chance the gradient is getting zeroed out.
  2. Don't trust loss readouts in the presence of mask-related fixes. The PR #610 NaN-guard returns 0 for fully-masked batches — gradient-correct, but it pulls the EMA toward zero and disguises a broken pipeline as fast convergence. We were three hours in before noticing.
  3. Disable evals you don't need. Pass --eval-every=-1 --eval-tokens=0 --chatcore-every=-1 for any run where you don't specifically want benchmark numbers. On constrained hardware this saves more wall-clock than any other tweak.
  4. caffeinate -i for any run over ten minutes. macOS App Nap will quietly suspend a process the kernel decides is idle. Caffeinate prevents this. Cheap, correct.
  5. Clean up between runs. Killing a Python process can leave multiprocessing workers and Metal contexts behind. pgrep -lf python before launching anything new.
07 / Next phase

Where to go from here

The natural extensions, ranked by interestingness-per-effort:

Run RL on top of SFT (scripts.chat_rl). The mode-collapse and "cending" loop behaviors we saw at low temperatures are exactly what PPO is designed to flatten. The reward-model side of nanochat's recipe is small; might surface more bugs of the same flavor.

File the dataloader fix upstream. The buffer lockup will silently break SFT for anyone running with max_seq_len < median conversation length on the smol-smoltalk dataset. Two-line patch with clear repro.

Try larger --depth. The M2 had no memory pressure at d6. d12 (≈300M params, GPT-1 sized) might fit in 24GB; the memory math says yes but Metal driver behavior at higher batch sizes is the unknown. Pretraining time would scale roughly 4×, so an overnight run.

Add token-weighted EMA logging. Right now the displayed loss is a per-step EMA that doesn't weight by n_valid. With masked SFT, partial batches contribute the same as full ones, which can mislead. Token-weighted EMA would surface actual per-token loss faithfully and keep us from re-discovering Incident 02 through trial-and-error next time.
