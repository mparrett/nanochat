The recipe was wrong.
Twice.

Date 2026-05-05
Hardware MacBook M2, 24GB
Branch experiment/hope-nested-learning

The Hope/Nested-Learning track had wrapped the day before — synthesis doc committed, ADR-004 (z-loss-as-standby) landed, no architectural appetite left in the tank. So we picked up a small leftover from the d8-extension ticket: d3 as a fast-iteration smoke platform. Forty-five minutes of compute, a chat-able tiny LM at the end, and a chance to see what kind of silly text comes out of a model 1/8 the size of d6. The plan was tidy. The launch script was not.

"Pre-flight clean: no orphan workers, all flags present, 33 GB free disk. Ready to run later tonight." — commit 0aa98df, the recipe doc, six minutes before the first launch
01 / Why a smoke at all

The carve-out from the d8 ticket

The session-6 wrap left three forward-work tickets standing: feat_d8_extension.md (keep the architectural question alive at scale), feat_modernization_alignment.md (zero-cost alignment with 2026 LLM templates), and a small carve-out inside the d8 ticket itself — "d3 might come in handy, but only as a pure plumbing/harness rig, not for architectural-question work." At d3 the memory layer is 33% of the network versus 16% at d6; any architectural conclusion gets structurally over-weighted.

The trade we wanted to test was simpler. Forget architectural conclusions. Just: can we run end-to-end, cold to chatbot, in well under an hour, on a model small enough to be entertainingly bad at everything? If yes, d3 becomes a reusable harness for any future instrumentation change — new probes, eval modes, save-policy tweaks — without paying the d6 wall every time. The recipe doc was the durable artifact; the run itself was the validation.

Sizing comes out cleanly from --depth=3: n_embd=192, three heads of width 64, three transformer blocks. Roughly 7.6M params on the architectural side, plus a 6.3M embedding table. Chinchilla-budget at --target-param-data-ratio=12 auto-resolves to about 900 iters; we set 1500 explicitly to give the model a bit more horizon than pure memorization.

02 / The recipe-first ritual

Lock the doc, then launch

The codebase has been bitten enough times by recipe drift that the standing convention is: markdown writeup first, run second. So the d3 smoke got its own doc — pre-flight checklist (no orphan Python or wandb workers, 33 GB free, no clobber on the d3_smoke tag), Recipe A (vanilla pretrain + SFT), Recipe B (with memory at layer 1, conditional only on validating memory plumbing), expected wall time, sample chat prompts, what to record. Committed at 0aa98df with a "ready-to-launch" status line.

The launch was supposed to be six minutes of paste-and-run. Forty-five minutes of training. Three silly chat outputs. Done by dinner.

03 / Bug #1

Bare torchrun on MPS doesn't init the dist process group

The recipe used torchrun --standalone --nproc_per_node=1 -m scripts.base_train — the pattern documented in the historical Stage 2 launch commands. First launch died after the model loaded, the embedding table allocated, the first validation pass at val_bpb 3.194 printed cleanly, and the optimizer took its first step: 

File "/Users/matt/projects-new/3p/nanochat/nanochat/optim.py", line 560, in step
    rank = dist.get_rank()
  ...
ValueError: Default process group has not been initialized,
            please make sure to call init_process_group.

The optimizer's step() calls dist.get_rank() and dist.get_world_size() unconditionally. Both require init_process_group. And in nanochat/common.py::compute_init: 

is_ddp_requested, ddp_rank, ddp_local_rank, ddp_world_size = get_dist_info()
if is_ddp_requested and device_type == "cuda":
    dist.init_process_group(backend="nccl", device_id=device)
else:
    device = torch.device(device_type)  # mps|cpu

On M2 / MPS, device_type != "cuda", so the second clause runs — no init_process_group call, even though torchrun has dutifully populated RANK, LOCAL_RANK, and WORLD_SIZE in the environment. The optimizer crashes on the first step.

Pulled the d6_baseline_modern launch command from docs/hope_nl_a3_a3prime_2026-05-05.md. The canonical M2 pattern is direct python: 

PYTHONUNBUFFERED=1 nohup uv run python -u -m scripts.base_train \
    --run=baseline-d6-modern --model-tag=d6_baseline_modern \
    --depth=6 --head-dim=64 --max-seq-len=512 --window-pattern=L \
    ...

No torchrun. The d6 runs that landed under the modern recipe — A3 seed=1, A3 seed=2, A3' baseline — all used uv run python -u -m directly. The Stage 2 pretrain commands that did use torchrun (in the older HANDOFF entries) presumably worked because the earlier optimizer code had a non-DDP path; the recent MuonAdamW consolidation removed it. Or because they ran from an activated venv where torchrun resolved to .venv/bin/torchrun instead of the homebrew one. Either way, post-A3 the canonical M2 pattern is direct python, and the recipe was built against the wrong precedent.

04 / Bug #2

Default flags ≠ canonical d6 — the --inherit-from fix

Re-launched without torchrun. New error, deeper in the script: 

File "/.../scripts/base_train.py", line 452, in <module>
    assert total_batch_size % world_tokens_per_fwdbwd == 0
AssertionError

--total-batch-size=16384, --device-batch-size=32, world size 1. So world_tokens_per_fwdbwd = 32 * max_seq_len. For the assertion to pass, max_seq_len needs to be 512 — and the d6 canonical recipe uses 512. Except base_train.py's default for --max-seq-len is 2048. Multiplied through: 32 * 2048 = 65536, and 16384 % 65536 ≠ 0. Crash before training begins.

Pulled the canonical d6 user_config from the d6_baseline_modern meta file. Three departures from the base_train.py defaults stood out:

flagscript defaultcanonical d6effect at d3
--max-seq-len 2048 512 assertion fails outright
--head-dim 128 64 n_embd=256 vs intended 192; 2 heads vs 3
--window-pattern SSSL L local/global alternation that d6 didn't use

The reflex was to add three more flags to the recipe. The better instinct was to recognize this as exactly the class of bug --inherit-from was built to prevent. The mechanism — landed in commit ca9bc94 at the start of the A3 multi-seed sweep — loads a reference meta_*.json as parser defaults before CLI parsing, so any unspecified flag inherits from a known-good run; CLI overrides win for what's intentionally different.

Final launch command, six lines instead of fifteen: 

PYTHONUNBUFFERED=1 nohup uv run python -u -m scripts.base_train \
    --inherit-from=$HOME/.cache/nanochat/base_checkpoints/d6_baseline_modern/meta_005000.json \
    --depth=3 \
    --num-iterations=1500 \
    --eval-every=100 \
    --save-every=500 --save-keep-last-n=2 \
    --seed=42 \
    --model-tag=d3_smoke --run=d3_smoke \
    > /tmp/d3_smoke_pretrain.log 2>&1

Thirty-four fields auto-loaded from the d6 meta — head_dim=64, max_seq_len=512, window_pattern=L, every learning-rate scalar, the warmup and warmdown schedule. --depth=3 is the only architectural override; the rest are per-run knobs (run name, seed, save policy, iteration count). The same approach handled SFT, inheriting from d6_baseline_modern_sft/meta_000375.json. Two recipes, same shape.

Launched. Step 26 of 1500. Loss 9.11, descending. ETA 25 minutes. The discipline paid off in the failure.

05 / The clean run

What 63 minutes of d3 looks like

Pretrain finished in 32.9 minutes (the recipe estimate had said 25-30; MPS dispatch overhead at d3 is essentially the same as d6, so the per-iter wall doesn't drop in proportion to model size). SFT chained automatically on success and ran 29.5 minutes (the recipe had estimated 12-18; SFT at total_batch_size=65536, accum=4 is dominated by four micro-batch fwd/bwd passes per step — batch-size-limited, not model-size-limited at d3). Total cold-to-chatbot: 62.4 minutes. Updated the recipe's estimate band to ~60-65 min for any future d3 smoke on this M2.

metricd3 smoked6 baselinegap
pretrain val_bpb @ final 1.3766 1.1686 +0.21
SFT val_bpb @ final 0.7753 0.6483 +0.13
pretrain wall 32.9 min~4 h ~7×
SFT wall 29.5 min~60 min ~2×
final pretrain checkpoint 101 MB 800 MB ~1/8

The +0.21 / +0.13 val_bpb gap is the gap a smaller-and-shorter-trained model produces; nothing more. The wall-time shape — pretrain 7× faster, SFT only 2× faster — is the actually-interesting datum. d3 is not a uniformly-faster d6; it's a faster pretrain platform tied to a roughly-the-same SFT cost. For any harness change that touches SFT specifically, the time savings are smaller than the per-token compute argument suggests.

06 / The silly outputs

Three prompts, three failure modes

The chatbot was the payoff, and the failure modes were each their own little portrait of "model knows part of the structure, doesn't have the capacity to finish it cleanly." Verbatim from chat_cli:

Q · "What is the capital of France?" "France is the capital of France. It is the capital of France. France is Paris. Paris is a city known for its historical landmarks and historical landmarks. Paris is the most iconic landmarks in the city is the largest city in the city. Paris is a city known for its historical landmarks and cultural institutions."

The factual association between "France" and "Paris" is there — the model emits "France is Paris" partway through. But the structural priors are weak enough that it can't get to it on the first try. It runs through "France is the capital of France" twice (wrong direction, syntactically fine) before self-correcting. Then degenerates into the landmark-loop. A bigger model would either get the answer cleanly or fabricate plausibly; d3 stutters its way to a partially-right answer through a tunnel of repetition.

Q · "Spell 'banana' letter by letter." "leana' letter by letter.:l,e,a,n,a,l,i,n,g,e, letter."

Drops the leading "B" entirely (leana), but does pick up the letter-by-letter format from SFT. Output letters: l, e, a, n, a, l, i, n, g, e. Positions 2–5 (e, a, n, a) are correct — the middle of "banana." Everything else drifts. The SpellingBee training fingerprint is faintly visible; the capacity to spell is not.

Q · "Once upon a time" "The time of a time is taken to a time to find a time spent in time. It takes a time to start, time, and minutes, and minutes to minutes... [the word "minutes" then repeats roughly fifty times, filling the context window]"

Pure repetition death-spiral. Latches onto "minutes" and runs it into the wall of the 512-token max. Classic small-LM failure mode and, at d3, the most likely outcome on any open-ended prompt. Pure entertainment.

None of these are quotable as Hope/NL evidence — the architectural question is settled at d6, and d3 numbers don't transfer regardless. They are the entertainment value the recipe doc promised, and they are also a useful calibration: if you ever want to know what a model with about 8 million transformer parameters does on a chat prompt, this is what that looks like.

07 / Takeaways

What stays after the chatbot is shut down

  1. Doc-then-launch caught two real bugs in twelve minutes. Both bugs were in the launch script pattern, not the architecture. Both would have been silent on a small typo or buried under a different runtime path. Writing the recipe doc before launching, locking it as a commit, then trying to run it forced the failure into the visible foreground. The discipline isn't ceremony; it's how you get the surface area of "what the script actually does" into the conversation log instead of into your head.
  2. --inherit-from is a class-of-bugs solution. Bug #2 was three flag mismatches; the temptation was to add three flags. The better move was the meta-inheritance mechanism A3 had landed for exactly this purpose — it eliminates the entire category of "did I remember --max-seq-len=512" by construction. The lesson generalizes: any future architectural-experiment recipe should default to --inherit-from <reference_meta> with minimal overrides, not flag enumerations.
  3. Direct-python is the M2 canonical launch pattern. torchrun on Apple Silicon injects DDP environment variables, but compute_init only initializes the process group on CUDA. The optimizer's dist.get_rank() then fails on the first step. The d6_baseline_modern + A3 + A3' runs all use uv run python -u -m scripts.base_train directly. This isn't currently spelled out in any auto-loaded surface (CLAUDE.md, DEV.md, key_facts.md); the recipe doc commit captures it, but lifting it into key_facts.md would prevent the next session from rediscovering the same trap.
  4. d3 is harness platform, not research platform. The wall-time picture (pretrain 7× faster than d6, SFT only 2× faster) tells you what d3 is good for: validating instrumentation that touches the pretrain loop, training-script flags, save-policy changes, eval-mode tweaks. It is bad for anything where SFT cost dominates, and it is structurally invalid for architectural conclusions. The recipe doc carries this distinction explicitly; the result run validated it empirically.

The smoke run produced one final on-disk artifact pair (~/.cache/nanochat/base_checkpoints/d3_smoke/model_001500.pt at 101 MB; chatsft_checkpoints/d3_smoke_sft/model_000375.pt at 101 MB), one wandb pretrain run, one wandb SFT run, and a chat server still listening on port 8765. The Hope/NL track stays closed; the harness now has a fast-iteration rig if anything in feat_d8_extension.md ever activates. The recipe doc is the durable artifact. The run was the validation.
