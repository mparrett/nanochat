The instrument doesn't.

Result Stage 1 lands at parity, probe finds 2× gap

Field Report II ended at a wall: the optimizer is 79% of every iteration, the polar-express Newton-Schulz loop runs ten sequential GEMMs, and Metal can't fuse them. We had two ideas left — a small dispatch-count win, and a gradient-accumulation trick. Phase 3 chased both. Then we pivoted to the actual research arc — building Hope/Nested-Learning's mutable memory into nanochat, one stage at a time. Stage 0 plumbing landed clean. Stage 1's full pretrain landed at val_bpb parity with baseline. Then a Codex steer turned the question on its head: "your instrument is too blunt." We built a probe. The probe found something the LM perplexity couldn't see.

"Full LM val_bpb is too blunt for Hope/NL behavior. Before Stage 2, add a tiny diagnostic task/probe that can tell whether memory helps at all." — Codex, mid-arc
01 / Phase 3 wrap

Cleaning up the perf wall, finding two bugs

Three small experiments finished closing the perf detour. The headline wins were modest. The headline data was that what worked on SFT did not transfer to pretrain — and that we'd been silently truncating SFT runs by ~4× without noticing.

experimentresultstatus
ve_gate → AdamW (filter by name, not shape) 319 → 176 GPU dispatches/iter (−45%); steady-state iter wall 2469 → 2162ms (−12%) committed 840d3db
SFT accum=4 vs accum=1, iso-token B-iso val_bpb 0.6639 vs A 0.7568 (−12% rel); accum amortizes optimizer cost on in-memory data recipe locked

chat_sft.py model_config asdict fix Was hand-listing fields when serializing; missed hope_memory_layer; chat_cli couldn't reload Stage 1 SFT committed f143da2

The ve_gate finding was a Codex tip: the tiny (6,12) gating matrices were burning a whole Polar Express dispatch group for almost no compute. Moving them to AdamW (filtered by module name, not shape, so the split is stable) dropped the dispatch count harder than predicted — the small group was emitting ~143 dispatches, not the ~30-40 we'd expected. Wall savings smaller than the dispatch ratio because the removed dispatches were on tiny matrices, but real.

The accum split between SFT (works) and pretrain (regresses) was the more useful finding. The mechanism we thought we were exploiting — amortizing optimizer cost across more micro-batches — is real on SFT because the dataloader is in-memory. On pretrain it gets eaten by the streaming tokenizer/parquet path serializing 4× the I/O per opt step. Locked the pretrain recipe at accum=1, total_batch_size=16384 and moved on.

The --num-iterations bug bit us mid-experiment when our first accum=4 SFT A/B finished at step 94 instead of 375. The data generator's iteration counter increments per yield, and the training loop pulls grad_accum_steps yields per opt step. The same counter drove approx_progress which drove the LR schedule, so the truncated run completed a "valid" miniature schedule with no NaN — just a quietly different experiment than asked for. One-line fix at chat_sft.py:281; added an mby: field (microbatch-yield counter alongside the optimizer step counter) so any future drift between the two is immediately visible in the per-step log.

02 / Hope/NL Stages 0 + 1

Plumbing, an architecture swap, a parity result

Stage 0 is pure refactor: thread an optional memory_state through GPT.forward() and each block, returning a tuple iff the caller passed one. Conditional-tuple-at-the-GPT-boundary kept all eleven existing call sites (training loops, evals, inference, tests, dev profilers) bit-identical. Six contract tests pin the load-bearing guarantee: same loss, same logits, with vs without memory_state when no block actually carries memory. Took ~45 min — well under the 2.5–4h estimate.

Stage 1 swaps one block's MLP for LinearAttentionMemory: 

k_t, v_t, q_t = W_k x_t, W_v x_t, W_q x_t
M_t = M_{t-1} + v_t k_t^T              # alpha=1, eta=1, fixed
o_t = M_{t-1} q_t                      # read uses *previous* memory
y_t = W_o o_t

Implemented via the parallel form o_t = sum_{i<t} (k_i · q_t) v_i — equivalent to the recurrence above when alpha=1, M_0=0, but stays in one big causal-masked einsum. No Python token loop (per Codex's "avoid token loops from day one"). W_o zero-init so the architecture is bit-identical to baseline at step 0 and diverges as W_o trains.

Then we ran the actual experiment: a full 5000-iter d6 pretrain at the unchanged baseline recipe, with --hope-memory-layer=3. Output to a fresh model_tag so the existing baseline checkpoint was preserved untouched.

Within single-seed noise. The full 21-eval trajectory is monotonic, no NaN, no instability. SFT on top with the validated accum=4 recipe (now correct after the bug fix) landed at val_bpb 0.6712 vs d6_b_iso's 0.6639 — also +1.1% rel, also within noise.

Spun up chat_web on a second port, side-by-side with the original baseline, and started probing. Both produce shallow co-occurrence-driven output at this scale: "the capital of Paris is Paris," "the sky blue is a small blue, with vibrant lights." Stage 1 had a noticeably worse multi-turn coherence wobble on one probe — forgot what "it" referred to, gave a confidently wrong yes/no — but the unmodified baseline fell apart similarly after a couple turns. Operator's verdict: "phase confirmed working, at least to the extent the other is."

03 / The instrument problem

Codex's pivot: val_bpb is too blunt

Three plausible next moves: more pretrain seeds for the val_bpb gap, jump to Stage 2 (per-token learned α/η), or stop and take the win. Sent the result to Codex. He pushed back on all three.

"I would not spend M2 time on multi-seed Stage 1 confirmation unless someone wants to claim 'Stage 1 improves/regresses nanochat.' Right now the claim should be narrower: 'memory-state plumbing plus one strict-causal linear-memory block trains end-to-end with negligible quality delta.' One seed is enough for that.

Before Stage 2, add a tiny diagnostic task/probe that can tell whether memory helps at all: associative recall, delayed copy, key-value recall across 512 tokens, or a synthetic in-context binding task. Full LM val_bpb is too blunt for Hope/NL behavior." — Codex

This is the right reframe. Average per-token cross-entropy on a 24M-token SFT mixture is dominated by positions where the architectural choice doesn't matter — common bigram patterns, format tokens, function words. A 1% gap can be either real architectural divergence on the load-bearing positions or noise on the bulk. Cranking more seeds doesn't sharpen the question; it just narrows the noise band on the same blunt instrument.

Captured the decision as ADR-001 (the project's first formal architectural decision record): insert a Stage 1.5 between Stage 1 and Stage 2, design and run a synthetic recall probe, let the result inform Stage 2's design and stability defaults.

04 / Stage 1.5 — the probe

Multi-Query Associative Recall

Picked Multi-Query Associative Recall (MQAR), a standard from the linear-attention literature. Sequence layout: 

<bos> k_1 v_1 k_2 v_2 ... k_K v_K <sep> q_1 a_1 q_2 a_2 ... q_M a_M

Model sees a list of (key, value) pairs in the prefix, then a sequence of query keys; it must produce the value bound to each query in the lookup. With K=M=16, T=128, a held-out test set, and per-query argmax accuracy as the load-bearing measurement. Both arms train from random init — only varying input is hope_memory_layer.

Vocab choice avoided BPE complications: pulled keys from token IDs [1024, 1056), values from [2048, 2080), both well below where common subword merges live. Reused the existing 32k-vocab tokenizer/model so no architecture changes were needed.

v1 — task too easy

First run: 1000 iters per arm, eval every 100. Baseline saturated to 100% accuracy at step ~76. Killed early. The MLP wasn't doing the work — full self-attention was solving recall on its own. With T=128 the lookup is shallow enough that the top-layer attention can attend from query position back to where the key appeared and read the bound value directly. The architectural swap at L3 isn't load-bearing on this task.

The "final layer is always full-context" constraint in nanochat/gpt.py::_compute_window_sizes means even window_pattern='S' leaves the last layer at full attention. The probe can't be made attention-bottlenecked without a real architecture change to that constraint. So we pivoted from "does the memory block do recall" to "how does the swap affect downstream sample efficiency" — same task, finer eval cadence, shorter horizon.

v2 — convergence-speed comparison

Step 1 is bit-identical (loss 10.3988, acc 0.031) — same fixed seed, both architectures share their starting state because W_o initializes to zero and the memory block contributes exactly nothing at init. From step 26 onward they diverge.

The shape is the story. Baseline groks abruptly — between step 51 and 76, accuracy jumps from 0.111 to 0.999 in a 25-iter window. Stage 1 groks gradually — 0.131 → 0.632 → 0.863 → 1.000 across step 76 → 101 → 126 → 151. Different shape, not just shifted. Stage 1 reaches the same final answer, but takes ~2× the iterations to get there.

Best hypothesis: replacing the MLP at L3 (ReLU² nonlinearity) with LinearAttentionMemory (bilinear (k·q)v) removes one feature-shaping nonlinearity. Recall via attention requires the softmax-or-equivalent to select a position; the MLP's nonlinearity helps surrounding blocks shape representations into something attention can sharply select on. Stage 1's L3 block is doing a second causal-attention-like operation without softmax — not removing capability, just removing one of the nonlinear steps that make selection sharp. The model compensates via the remaining 5 MLP blocks, which it does, but slower.

05 / Takeaways

Where this leaves us

  1. Codex's "your instrument is too blunt" steer was correct and validated. The val_bpb gap (1.1% on SFT) hid a 2× sample-efficiency gap on a task where the architectural difference matters. We would have built Stage 2 on top of Stage 1 without knowing the swap incurs a real cost on recall-shaped problems. Now we know — Stage 2's gates have to recover that gap before claiming improvement.
  2. The probe is reusable infrastructure. Each arm runs in ~8 minutes. Any future architectural variant can be put through it as a fast gate before sinking 3 hours into a full d6 pretrain. If a Stage 2 variant doesn't recover at least baseline's MQAR convergence speed, we know to iterate before scaling up.
  3. Hope-flavored benefits don't show up at d6 / T=128 / full attention. The interesting Hope/NL claims — sub-quadratic effective context, test-time adaptation, recall-at-scale — live at scales we won't touch on this hardware, and require attention to be the bottleneck (which it isn't here). What we can validate at d6 is that the plumbing is sound and the architecture trains to parity. We did. Stage 1 is a solid foundation; whether we ride it to Stages 2-6 or stop here is now a clean decision.
  4. Two real upstream-relevant bugs found and fixed. The chat_sft.py --num-iterations micro-batch counting silently invalidated any A/B that varies --total-batch-size while passing --num-iterations; the model_config hand-listing was a latent footgun for any new GPTConfig field. Both fixed with minimal diffs; the bf16 fix from earlier is already filed as karpathy/nanochat#741.

Decision point now lives with the operator: (a) proceed to Stage 2 with the convergence-speed gap as a load-bearing constraint, (b) patch the always-full-final-layer constraint and re-run the probe attention-bottlenecked, or (c) wrap the arc here. Each is defensible. The repo is in a clean state for any of them.
