Field Report II  ·  nanochat performance on Apple Silicon

Closing the 3.6h → 30min gap.
How far does the M2 actually go?

Date 2026-04-30
Hardware MacBook M2, 24GB
Reference M3 Max, ~30 min
Result 17% faster, ceiling found

Phase 1 got nanochat training end-to-end on a 24GB M2. Pretrain took 3.6 hours against Karpathy's 30 minutes on M3 Max. Raw hardware accounts for ~3-4× of that gap; we suspected another 2× was hiding in software. Phase 2 went looking for it. Found ~17%, hit a hard wall, and learned exactly where the wall is.

"The optimizer is 79% of every iteration. The Newton-Schulz matmul loop in Muon's polar express runs 10 sequential GEMM kernels per call. torch.compile can't fuse them on Metal." — the bottleneck, in one line
01 / Phase 2 scoreboard

Every lever we tried

Seven experiments, ranked roughly by how much we wanted them to work. Three landed. Two were dead ends with useful data attached. Two are open follow-ups.

02 / The finding

The optimizer is the cost

We profiled a steady-state pretrain step on M2 and got a number that resolved most of our hypotheses at once:

phasems / iter%
forward43220.1%
backward170.8%
optimizer1,69679.1%

Forward is fast. Backward is essentially free. The entire wall-clock cost lives in optimizer.step, and within it, in muon_step_fused's polar express Newton-Schulz loop — a sequence of ns_steps matrix×matrix multiplications used to orthogonalize the matrix-parameter gradient.

On CUDA, torch.compile's Inductor fuses this loop into a single Triton kernel. On Metal, no such fusion exists — each matmul is its own kernel launch with its own dispatch overhead. We confirmed this directly: applying @torch.compile to muon_step_fused dropped CPU-side dispatch time by 22× but did not change wall-clock. The GPU is doing the work; it's just doing the work as 10 separate kernels per call instead of one.

This is the wall. Without Triton on Metal — and without rewriting the polar express in raw Metal — there isn't a software path to fuse it. M2's 24GB unified memory means we can't trade extra memory for fewer iterations either. The remaining ~3 hour pretrain floor is set by hardware and Apple's compiler stack.

03 / What worked

The two committed wins

WIN 01
committed +10% throughput

Pin optimizer scalars to the parameter device

The optimizer fills 0-D scalar tensors (lr_t, beta1_t, etc.) with hyperparam values each step. The original code keeps these on CPU so torch.compile's codegen can read them as compile-time constants without recompilation. On MPS, that meant our cherry-picked fix was moving the scalars CPU→MPS every single step — and a 0-D scalar move on MPS costs ~8.6 ms because of host-device sync.

The fix: lazy-init device-resident copies on the first step, then fill_() them in-place. We also replaced one add_(alpha=-step_size) call with sub_(... * step_size) because alpha= with a device tensor forces a .item() host fetch. 

def _pin_scalars_to_device(self, device):
    if self._scalars_pinned_to_param_device or device.type == "cuda":
        self._scalars_pinned_to_param_device = True
        return
    for name in ("_adamw_step_t", "_adamw_lr_t", # ...):
        setattr(self, name, getattr(self, name).to(device))
    self._scalars_pinned_to_param_device = True

Numerical equivalence: loss at SFT step 1 was 1.890413 with both the original and patched code, identical to 6 decimals. Net throughput on d6 pretrain: 2.3 → 1.9 s/iter.

WIN 02
committed robustness

PR #145 optim cherry-pick (no perf, but real safety)

Earlier we tried TORCHDYNAMO_DISABLE=1 to skip torch.compile and immediately hit a CPU-vs-MPS device error inside the AdamW kernel — the original code was relying on Inductor's codegen to silently handle scalar promotion. PR #145's _cuda_compile decorator + explicit scalar-to-device move makes the eager path correct on MPS. It doesn't speed anything up, but it means we can run with or without compile. That option is what enabled experiment WIN 01 above.

04 / What didn't

The four dead ends (with notes)

DEAD END 01
memory ceiling

device_batch_size > 32 doesn't fit on 24GB

Larger batch is usually free throughput up to the memory wall. We expected the wall to be much further out — the model is only ~73M params (~1 GB working set). It's not. batch=48 ran at 67 s/iter (memory thrashing); batch=64 hit a 22.6 GB physical footprint and stalled. Activation memory at fp32 with no Flash Attention is much higher than the parameter count suggests.

DEAD END 02
no Metal fusion

torch.compile on the Muon kernel specifically

We hoped Inductor would fuse the Newton-Schulz matmul loop into a single Metal kernel. CPU-side dispatch dropped from 220 ms → 10 ms per iter — real, but the wall-clock didn't move. The matmuls still run as 10 separate kernels per call; only Python overhead went away. Metal's compiler stack doesn't have an equivalent to Triton's loop-fusion.

DEAD END 03
mixed-precision plumbing

NANOCHAT_DTYPE=bfloat16 on M2 MPS

An open issue (#685) reports bf16 working on M4 Max with ~25% memory savings — which would in principle unlock device_batch_size=48 for us. On M2 it fails immediately: 

'mps.multiply' op requires the same element type for all operands and results
%4 = "mps.multiply"(%arg2, %3) : (tensor<1xbf16>, tensor<3x1x12xf32>) -> ...

nanochat's bf16 path keeps master weights and optimizer state in fp32 but casts activations and some optimizer buffers to bf16. CUDA implicitly promotes mixed-dtype operands; Metal hard-fails. Fixing this would require auditing every * / lerp_ / add_ in optim.py and gpt.py for mixed-dtype operands and inserting explicit casts. Real engineering work — out of scope for Phase 2 but the highest-leverage outstanding lever if we want to push further on this hardware.

DEAD END 04
interesting datum

Cherry-picking PR #145 wholesale

PR #145 also gates model-level torch.compile behind device_type == "cuda" on the theory that compile is "unsupported on MPS and pointless on CPU." We applied it, ran a 5-iter probe, and got ~4 s/iter instead of the usual ~2 s/iter. torch.compile on the model itself is a real ~2× win on M2, even with the warmup tax. Reverted that part of the PR; kept the optim parts.

DEAD END 05
defaults win decisive measurement

MPS env vars (PREFER_METAL, FAST_MATH) all hurt

The PyTorch MPS module exposes opt-in env vars that I had high hopes for. PYTORCH_MPS_PREFER_METAL=1 bypasses MPS Graph and goes straight to Metal kernels for matmuls. PYTORCH_MPS_FAST_MATH=1 relaxes IEEE 754 strictness. Both sounded like clear wins for our matmul-heavy optimizer. Both made things worse:

configs/itervs baseline
baseline2.211.00×
PREFER_METAL=110.350.21× (5× slower)
FAST_MATH=13.070.72× (40% slower)
both5.600.39× (2.5× slower)

The result is the opposite of my prediction — and inverts our intuition about the bottleneck. I had assumed MPS Graph was adding overhead and direct Metal would be faster. In fact, MPS Graph is doing real fusion and batching that direct Metal kernels don't get. For a polar express loop of stacked-tensor matmuls, the graph layer's batched dispatch beats raw Metal. FAST_MATH=1 being slower is more surprising — possibly because fast-math kernels disqualify graph fusion or are tuned for half-precision rather than fp32.

The takeaway: the MPS defaults are well-tuned for our specific workload. The opt-in tuning knobs in PyTorch 2.9.1 are aimed at different workloads (probably large single-matmul inference). This rules out the entire class of "low-level MPS kernel tuning" as a Phase 2 lever and pushes any further work toward upgrading the framework itself.

05 / Open follow-ups

Three things worth pursuing

Upgrade to PyTorch 2.11 (cheapest, doing it next)

PyTorch 2.11 (March 2026) explicitly migrates many MPS ops from MPSGraph to native Metal kernels by default. That's the same direction as PREFER_METAL=1, but applied selectively to ops where the migration actually helps — not blanket-applied like the env var. There are also targeted SDPA correctness fixes (#174945) and broader bf16 support, both of which could unblock our parked bf16 attempt. Cost: 10–15 minutes if dependencies cooperate; 1–2 hours if there are version conflicts. This is Phase 2's natural off-ramp into Phase 3.

Validate ns_steps=3 properly

Reducing Muon's Newton-Schulz iterations from 5 → 3 produced loss values identical to 6 decimals over 9 SFT steps, with ~12% optimizer speedup. The polar express coefficients are tuned for 5 iters per the original paper — using only the first 3 is theoretically suboptimal even though it's empirically identical at this scale. We need a real A/B: pretrain to step 5000 with ns_steps=3, compare final val_bpb against our existing baseline of 1.174. Cost: ~3 hours overnight. Ticketed in docs/project_incoming/feat_muon_ns_steps_validation.md.

The bf16 mixed-precision audit

If bf16 works with proper plumbing, it could unlock both larger batch (memory) and maybe faster matmul kernels (compute). The work is real but bounded — it's a half-day of careful editing in optim.py and gpt.py, plus a numerical-stability test. Worth doing if we want another serious attempt at closing the gap, or if anyone wants to send a more careful version of this fix upstream. Note: if PyTorch 2.11 fixes the underlying Metal Graph issue, this audit may not be needed at all.

06 / Reflection

What we'd do differently

  1. Profile first, hypothesize second. We started Phase 2 with a list of plausible levers (batch size, dtype, attention backend) and tested them in vague order. The single most useful artifact in this whole session was the torch.profiler trace that showed optimizer = 79%. We should have run it first and let the data direct the search.
  2. Cherry-pick PRs surgically, not wholesale. PR #145 has multiple changes bundled together. Wholesale-applying it broke our throughput; surgical-applying it (just the optim parts) gave us a robustness improvement. Reading PRs as a menu of choices, not an all-or-nothing patch, is the right mental model.
  3. Question your speedup assumptions. We expected ns_steps=3 to be ~40% faster (it was 12%). We expected larger batch to help (the memory wall arrived 50% earlier than predicted). The model was tiny on paper but activation memory was big in practice. Always measure before celebrating.
  4. Identical loss to 6 decimals is suspicious. Investigate it. When ns_steps=3 produced bit-identical loss vs ns_steps=5, the right reaction was "interesting, what's actually happening?" — not "free speedup, ship it." The Newton-Schulz iteration is converging to numerical precision in 3 steps for these matrix shapes; that's a real and useful finding, but it deserves a proper full-pretrain validation before trusting it.
  5. The wall is the wall. ~3 hours pretrain on M2 24GB with the current codebase. Hardware (cores, bandwidth) accounts for most of the M2 vs M3 Max gap; software accounts for ~17%. There's no magic 2× hiding in the optimizer config — it's hiding in Apple Silicon's compiler stack (Triton equivalent) or in nanochat's bf16 path on MPS, neither of which we can fix in a Phase 2 sprint.
