# Reproducing nanochat on M2 24GB — 2026-04-30

End-to-end run of `runs/runcpu.sh` on a MacBook M2 24GB (Karpathy's recipe was tuned for M3 Max). The pipeline works, but three real bugs and a few operational gotchas had to be sorted first. This doc is the field report.

## Result

- **Base model** (d6, 73M params): val_bpb 1.174 after 5000 pretrain iters (~3.6h)
- **SFT model**: 1500 iters with the dataloader fix (~66 min)
- **Smoke test:** `python -m scripts.chat_cli -p "What is the capital of France?"`
  > "The capital of France is Paris. It is a city known for its historical landmarks and cultural institutions such as the Eiffel Tower and the Louvre Museum..."

Coherent, correct, slightly repetitive. About what you'd expect from 73M params trained for ~4.5 hours.

## Hardware / environment

- MacBook M2, 24GB unified memory, macOS Darwin 25.4.0
- PyTorch 2.9.1, MPS backend (auto-detected)
- `COMPUTE_DTYPE: torch.float32` (no bf16 on MPS — same as M3 Max)
- No Flash Attention 3 — SDPA fallback

## Pipeline summary (the commands that actually worked)

```bash
uv venv && uv sync --extra cpu
source .venv/bin/activate

# Data
python -m nanochat.dataset -n 8                          # ~800MB, 9 shards
python -m scripts.tok_train --max-chars=2000000000       # ~80s
python -m scripts.tok_eval                               # sanity

# Pretrain (~3.6h)
PYTHONUNBUFFERED=1 python -u -m scripts.base_train \
    --depth=6 --head-dim=64 --window-pattern=L \
    --max-seq-len=512 --device-batch-size=32 --total-batch-size=16384 \
    --eval-every=500 --eval-tokens=262144 \
    --core-metric-every=-1 --sample-every=500 \
    --num-iterations=5000 --run=dummy

# Identity convs for SFT
curl -L -o ~/.cache/nanochat/identity_conversations.jsonl \
    https://karpathy-public.s3.us-west-2.amazonaws.com/identity_conversations.jsonl

# SFT (~66 min) — REQUIRES the dataloader patch and PR #610 NaN-fix below
PYTHONUNBUFFERED=1 caffeinate -i python -u -m scripts.chat_sft \
    --max-seq-len=512 --device-batch-size=32 --total-batch-size=16384 \
    --eval-every=-1 --eval-tokens=0 --chatcore-every=-1 \
    --num-iterations=1500 --run=dummy

# Talk to the model
python -m scripts.chat_cli -p "What is the capital of France?"
```

Key flags vs. `runs/runcpu.sh`:
- `--eval-every=500 --eval-tokens=262144` (lighter than default)
- SFT: `--eval-every=-1 --eval-tokens=0 --chatcore-every=-1` (skip all evals)
- `caffeinate -i` to prevent macOS App Nap from suspending the long SFT run
- `PYTHONUNBUFFERED=1` so you actually see iter prints in real time

## Bugs hit (in encounter order)

### 1. `F.cross_entropy` NaN on fully-masked batches — upstream issue #590

**Symptom**: SFT loss = NaN at step 4, deterministically, regardless of LR / warmup / optimizer-state inheritance.

**Cause**: When all targets are `-1` (ignore_index), `F.cross_entropy(reduction='mean')` divides by zero → NaN that propagates and freezes training. Karpathy's M3 Max recipe doesn't reliably trigger this; M2 (or any setup with smaller batches) does.

**Fix**: Applied [PR #610](https://github.com/karpathy/nanochat/pull/610), 2-line patch in `nanochat/gpt.py`:

```python
if loss_reduction == 'mean' and not (targets != -1).any():
    return logits.sum() * 0.0  # graph-connected zero, no NaN
```

### 2. SFT bestfit dataloader buffer lockup — our discovery

**Symptom**: SFT runs through the whole 1500 iters with no NaN and a beautiful-looking decaying loss... but the resulting model is gibberish (`"juven neurotransmit�esterol meticul..."`).

**Cause**: After applying fix #1, instrumented `n_valid` per step. Found that **steps 1–3 had real targets (~20% valid), and every step from 4 onwards had `n_valid = 0`** — i.e., every batch was fully-masked. Bug is in `sft_data_generator_bos_bestfit`: the buffer holds 100 conversations and only pops them when one fits in `row_capacity=513`. SmolTalk has many conversations longer than 513 tokens. Once the small ones drain (steps 1–3), the buffer permanently locks with over-length convs, every row gets BOS-padded (mask=0), `consumed` never advances, and the model receives zero gradient updates for the rest of training. PR #610's fix made this *silent* by returning 0 for fully-masked batches, so the EMA decayed to zero and looked like fast convergence.

**Fix**: Patch in `scripts/chat_sft.py` — when `len(row) == 0` and no conv fits, all buffered convs must be over-length. Discard them so `refill_buffer` can pull fresh data:

```python
elif len(row) == 0:
    n_dropped = len(conv_buffer)
    consumed += n_dropped * ddp_world_size
    conv_buffer.clear()
    continue
```

After fix: median 29% valid tokens/step (range 16.7–36.4%), 0 fully-masked steps. Loss descended 1.89 → 1.40 over 1500 iters. **Worth filing upstream** — current code silently fails on any setup where `max_seq_len < median conversation length`.

### 3. `chat_sft` defaults that nuke your wall-clock

`--chatcore-every` defaults to **200**. On M2 the full ChatCORE benchmark suite (ARC + MMLU + GSM8K + HumanEval + SpellingBee) takes ~hours per pass. Pass `--chatcore-every=-1` to skip.

`--eval-every=-1` skips intermediate val evals but **does not skip the eval at `last_step`** (the condition is `last_step or ...`). Default `--eval-tokens=40*524288` ≈ 21M tokens ≈ ~30 min on M2. Pass `--eval-tokens=0` to also skip the final eval (returns `inf` cleanly; save block still runs).

## Operational gotchas (not bugs, but cost time)

- **macOS App Nap**: long-running training with no foreground attention got suspended once. `caffeinate -i` on the command keeps it warm.
- **Orphan workers from killed runs**: a multiprocessing worker from an earlier debug probe stayed running for ~3 hours at 22% CPU, hogging the Metal context, causing the next SFT to hang at 0% CPU after step 1. Always `pgrep -lf python` between runs and clean up.
- **`taskpolicy -c utility -p <pid>`**: lets training run full-tilt when idle but yields the GPU to foreground apps. Recommended for long runs.
- **GPU% looks pegged because that's normal**: M2's GPU at 100% during training is expected and intended; the QoS demote is a contention-only relaxation, not a hard cap.
- **`tee` line-buffering**: `python ... | tee log` is fine, but `python ... | tail` traps stdout in `tail` until the source closes. Use `tee` for logs.

## Time / disk budget

| Phase | M3 Max (Karpathy) | M2 24GB (us) | Disk added |
|------|---|---|---|
| Dataset download | minutes | ~3 min | ~800MB |
| Tokenizer train | ~34s | ~80s | ~MB |
| Pretrain (5000 it) | ~30 min | ~3.6h | ~800MB ckpt |
| SFT (1500 it) | ~10 min | ~66 min | ~800MB ckpt |
| Total | ~45 min | ~5h+ | ~3GB |

3–5× slower on M2 vs M3 Max, which matches the GPU core / memory bandwidth ratio.

## What I'd do differently next time

1. **Instrument first.** When loss decays to weirdly low values, add `n_valid` logging *immediately* — don't wait an hour for the run to finish on a model that's getting zero gradient updates.
2. **`--chatcore-every=-1 --eval-every=-1 --eval-tokens=0`** unless you specifically want benchmark numbers. Saves hours.
3. **Always `caffeinate -i`** for any run >10 min on a Mac.
4. **Don't trust the loss display** in the presence of mask-related fixes. The PR #610 NaN-guard returns 0, which is honest for the gradient (no update) but pulls the EMA toward zero and disguises a broken pipeline as "fast convergence."
5. **Clean up zombies between runs.** A leftover multiprocessing worker can pin a Metal context and stall the next launch silently.
